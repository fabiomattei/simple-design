Packaging

Three ways to package the app: a per-user install on Linux, a sandboxed Flatpak, and a macOS .app/.dmg.

Wayland only resolves a window's icon through a .desktop file matched by the window's app_id — there's no other mechanism for a toolkit to hand the compositor an icon directly. src/main.rs sets with_app_id("simple-design") for exactly this reason; both packaging methods below rely on it matching a .desktop file's StartupWMClass.

So that even cargo run gets an icon, the app also writes the icon and ~/.local/share/applications/simple-design.desktop itself at startup (src/desktop_entry.rs). It points that entry at its own binary only when there is no entry yet, when the entry's program no longer exists, or when the entry launches a cargo build (target/debug or target/release) and this copy is installed. A working entry for another copy is never taken over, so running a build from the checkout doesn't hijack the applications menu from the installed app.

Desktop entry (unsandboxed)

The plain option: a per-user install under ~/.local, no root and no sandboxing. Files live in packaging/linux/.

FilePurpose
simple-design.desktopTemplate with an __EXEC_PATH__ placeholder
install.shBuilds the release, then installs the binaries, icon and desktop entry
./packaging/linux/install.sh              # cargo build --release, then install
./packaging/linux/install.sh --no-build   # install an existing target/release build
./packaging/linux/install.sh --uninstall  # remove everything it installed
InstalledWhere
simple-design, simple-design-cli~/.local/bin/
Icon (assets/icon/simple-design.png)~/.local/share/icons/hicolor/512x512/apps/simple-design.png
Desktop entry (Exec=… %f, Icon=simple-design)~/.local/share/applications/simple-design.desktop

Set PREFIX to install somewhere other than ~/.local. The installed copy doesn't depend on the checkout. To update it, re-run the script after pulling. If the icon still doesn't show up after installing, log out and back in, or restart GNOME Shell (Alt+F2, r). The shell caches app icons.

Flatpak (sandboxed)

The distributable Linux option: a real Flatpak app, io.github.fabiomattei.simple-design, built entirely from this repo. It needs nothing installed on the user's system besides Flatpak: the org.freedesktop.Platform runtime provides every library the app loads at startup (Wayland/X11, libxkbcommon, Vulkan/EGL, libdbus). Files live in packaging/flatpak/.

FilePurpose
io.github.fabiomattei.simple-design.ymlThe build manifest. Installs both binaries, the icon (assets/icon/simple-design.png), the desktop entry, the metainfo and the MIME type
io.github.fabiomattei.simple-design.desktopFlatpak-specific desktop entry (Exec=simple-design %f, Icon and StartupWMClass = the app id, MimeType=application/x-sdesign)
io.github.fabiomattei.simple-design.xmlRegisters *.sdesign as application/x-sdesign, so files open in the app from a file manager
io.github.fabiomattei.simple-design.metainfo.xmlAppStream metadata (license, summary, releases)

Inside the sandbox (FLATPAK_ID set), src/main.rs uses the Flatpak's app id as the window's app id, so it matches the exported desktop entry, and skips writing its own entry (see above).

Build setup

Runtime: org.freedesktop.Platform / org.freedesktop.Sdk 25.08, plus the rust-stable SDK extension (installed once):

flatpak install flathub org.freedesktop.Sdk.Extension.rust-stable//25.08

Build & install

cd packaging/flatpak
flatpak-builder --force-clean --user --install builddir \
  io.github.fabiomattei.simple-design.yml

Run it with:

flatpak run io.github.fabiomattei.simple-design [file.sdesign]

To share it as a single file instead of installing it, export a bundle:

flatpak-builder --force-clean --repo=repo builddir io.github.fabiomattei.simple-design.yml
flatpak build-bundle repo simple-design.flatpak io.github.fabiomattei.simple-design
# on another machine: flatpak install --user simple-design.flatpak

The CLI in the Flatpak

simple-design-cli ships inside the Flatpak too:

flatpak run --command=simple-design-cli io.github.fabiomattei.simple-design file.sdesign list-layers
# shorter, in ~/.bashrc:
alias simple-design-cli='flatpak run --command=simple-design-cli io.github.fabiomattei.simple-design'

Live mode works across the sandbox in both directions. Inside a Flatpak, ipc/registry.rs puts the instance registry and sockets under $XDG_RUNTIME_DIR/app/<app id>/simple-design/, the one runtime folder Flatpak shares between every instance of the app and the host, at the same path on both sides. A CLI outside the sandbox (a native install) looks there as well as in its own folder, so it finds a sandboxed GUI too.

Sandbox permissions

  • --socket=wayland, --socket=fallback-x11 — display access
  • --device=dri — GPU access for the wgpu renderer
  • --share=ipc — required alongside the display sockets
  • --filesystem=home — for the CLI. The GUI alone would manage without it: rfd (the file-dialog crate) uses the org.freedesktop.portal.FileChooser portal, which grants access to whatever the user picks. But the CLI opens the paths named on its command line, which no portal can grant, and live mode keys instances by real file paths, which portal-granted files don't keep. Inkscape's and GIMP's Flatpaks grant the same.

Known limitation: not Flathub-ready

The manifest builds with --share=network and lets cargo build --release fetch dependencies from crates.io live, inside the sandbox, on every clean build. That's fine for local use but is exactly what Flathub's review process rejects — submissions must build with network access disabled, which means vendoring every crate as a manifest source (typically generated from Cargo.lock via flatpak-cargo-generator into a generated-sources.json included as a module source). That step hasn't been done here.

macOS (.app and .dmg)

A macOS build needs no libraries on the user's Mac: the app draws with Metal and otherwise links only system frameworks, and Rust links its own code statically. Files live in packaging/macos/.

FilePurpose
Info.plistBundle metadata, with a __VERSION__ placeholder filled from Cargo.toml
build-dmg.shBuilds a universal (Apple Silicon + Intel) Simple Design.app and a drag-to-Applications .dmg into target/macos/

Run it on a Mac with rustup and Xcode's command-line tools (xcode-select --install):

./packaging/macos/build-dmg.sh

Without signing settings the app is only ad-hoc signed. That runs on the Mac that built it, but Gatekeeper blocks it on others until the user allows it in System Settings > Privacy & Security. To distribute it, sign and notarize with an Apple Developer account: 

# once: store notarization credentials in the keychain
xcrun notarytool store-credentials simple-design-notary \
  --apple-id you@example.com --team-id TEAMID --password <app-specific password>

CODESIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
NOTARY_PROFILE=simple-design-notary \
  ./packaging/macos/build-dmg.sh

The CLI sits inside the bundle. To use it from a terminal, link it onto the PATH: 

sudo ln -s "/Applications/Simple Design.app/Contents/MacOS/simple-design-cli" /usr/local/bin/

Live mode works as on Linux. Without $XDG_RUNTIME_DIR, the sockets live in the per-user temporary folder.

Known limitation: opening files from Finder

.sdesign files aren't registered with the app, on purpose. Finder doesn't pass a double-clicked file on the command line; it sends an open documents Apple Event, which winit (under eframe) doesn't forward. Registering the type would make a double-click launch an empty window. Wiring that event up needs an Objective-C application-delegate hook, which should be written and tested on a Mac. Until then, open files with File > Open or open -a "Simple Design" --args file.sdesign.
